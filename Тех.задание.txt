# Техническое задание: развитие Mirei AI — центрального интеллектуального управления Discord-сервером

## 1. Основная идея проекта

Mirei — это искусственный интеллект, встроенный в Discord-бота. Сейчас ИИ работает относительно независимо от остальных систем бота.

Главная задача проекта — превратить Mirei в центральный интеллектуальный интерфейс управления Discord-сервером, который будет связан со всеми существующими модулями.

Mirei должна понимать запросы пользователей на обычном человеческом языке, определять, какой модуль необходим, получать от него информацию или инициировать действие.

Пример:

Администратор пишет:

«Mirei, покажи, сколько сегодня пользователей прошло верификацию».

Mirei должна:
1. Понять запрос.
2. Определить, что требуется модуль верификации.
3. Получить необходимые данные.
4. Сформировать понятный ответ.

Другой пример:

«Mirei, забань пользователя за спам».

В этом случае Mirei должна проверить права инициатора, подготовить действие, запросить подтверждение и только после подтверждения выполнить бан.

**Главная концепция: пользователь общается с одним ИИ, а Mirei самостоятельно взаимодействует с различными системами Discord-бота.**

## 2. Уже существующие системы бота

В проекте уже реализованы следующие модули:

- Система верификации пользователей.
- Канал-ловушка для обнаружения подозрительных пользователей и ботов.
- Система автоматической выдачи ролей.
- Статистика Discord-сервера.
- Создание и управление приватными каналами.
- Система логирования событий.
- Искусственный интеллект Mirei.

Необходимо изучить существующую реализацию каждого модуля.

Не создавать дублирующие системы верификации, статистики, логирования, авторолей и других уже существующих функций.

Не переписывать рабочие модули без необходимости.

Задача — предоставить Mirei безопасный доступ к уже существующим возможностям.

## 3. Центральная архитектура Mirei

Необходимо создать промежуточный слой между искусственным интеллектом и существующими модулями.

Предлагаемая структура:

Mirei AI Core
- Понимание пользовательских запросов.
- Анализ контекста диалога.
- Определение намерения пользователя.
- Выбор необходимых инструментов.
- Формирование ответа.

AI Tool Router
- Реестр доступных инструментов.
- Определение нужного модуля.
- Передача параметров.
- Получение результатов.
- Обработка ошибок.

Security Layer
- Проверка прав пользователя.
- Определение опасности действия.
- Система подтверждений.
- Защита от повторного выполнения.
- Журналирование действий.

Module Adapters
- Verification Adapter.
- Trap Adapter.
- AutoRole Adapter.
- Statistics Adapter.
- PrivateChannel Adapter.
- Logging Adapter.
- Moderation Adapter.
- ServerConfig Adapter.

Existing Discord Bot Modules
- Существующие рабочие системы бота.

Важно: это логическое разделение ответственности. Конкретную структуру файлов необходимо определить после изучения реального проекта.

## 4. Взаимодействие Mirei с существующими модулями

### 4.1. Верификация

Mirei должна уметь:
- Показывать количество прошедших верификацию.
- Показывать количество ожидающих проверки.
- Получать информацию о конкретном пользователе.
- Выявлять проблемы в работе системы.
- Объяснять, почему пользователь не прошёл верификацию, если данные доступны.

### 4.2. Канал-ловушка

Mirei должна уметь:
- Показывать количество срабатываний.
- Находить участников, попавшихся на ловушку.
- Показывать время срабатывания.
- Анализировать события.
- Предоставлять статистику подозрительной активности.

### 4.3. Автоматические роли

Mirei должна уметь:
- Просматривать настройки автоматических ролей.
- Проверять наличие необходимых ролей.
- Определять возможные причины, по которым роль не была выдана.
- Показывать статистику выдачи ролей.
- Изменять настройки только при наличии соответствующих прав и подтверждения, если действие опасное.

### 4.4. Статистика сервера

Mirei должна получать:
- Количество участников.
- Количество активных участников, если такая статистика собирается.
- Динамику вступлений и выходов.
- Статистику сообщений.
- Данные об активности.
- Сравнение периодов, если доступна необходимая история.

Mirei должна уметь формировать текстовые отчёты и объяснять изменения активности.

### 4.5. Приватные каналы

Mirei должна уметь:
- Создавать приватные каналы.
- Показывать существующие приватные каналы.
- Изменять список участников с доступом.
- Управлять разрешениями.
- Удалять приватные каналы.

Создание, изменение прав и удаление должны проходить через систему проверки безопасности. Опасные действия требуют подтверждения.

### 4.6. Логи

Mirei должна уметь:
- Искать события по участнику.
- Искать события по типу.
- Искать события за определённый период.
- Показывать историю модерации.
- Находить информацию об удалённых сообщениях, если она сохранена.
- Формировать сводки событий.

Необходимо использовать существующую систему логирования, а не создавать параллельную.

## 5. Управление через обычный диалог

Mirei не должна ограничиваться заранее заданными командами.

Пользователь должен иметь возможность писать обычным языком.

Примеры:

«Mirei, кто сегодня присоединился к серверу?»

«Покажи, кто попался на ловушку за последние сутки».

«Почему у пользователя отсутствует роль?»

«Сколько человек было активно на этой неделе?»

«Создай приватный канал для администрации».

«Найди последние действия модератора».

«Покажи, какие модули сейчас работают».

Mirei должна самостоятельно определять, какой инструмент использовать.

Если запрос неоднозначен, она должна задать уточняющий вопрос.

Если данных недостаточно, она не должна придумывать ответ.

## 6. Обязательная система безопасности

Для Mirei выбран следующий режим:

**Опасные действия всегда требуют подтверждения пользователя.**

Необходимо разделить операции на три категории.

### Категория 1. Чтение информации

Примеры:
- Просмотр статистики.
- Получение информации об участниках.
- Поиск логов.
- Просмотр настроек.
- Анализ активности.

Подтверждение не требуется, если у пользователя есть права на получение соответствующей информации.

### Категория 2. Безопасные операции

Примеры:
- Формирование отчётов.
- Анализ данных.
- Получение диагностической информации.

Могут выполняться автоматически.

### Категория 3. Опасные операции

Примеры:
- Бан и кик.
- Мут и изменение наказаний.
- Выдача привилегированных ролей.
- Удаление каналов.
- Изменение разрешений.
- Массовое удаление сообщений.
- Изменение важных настроек сервера.

Обязательный порядок:

1. Проверка прав инициатора.
2. Проверка допустимости операции.
3. Подготовка параметров действия.
4. Создание уникального идентификатора операции.
5. Отправка сообщения с подтверждением.
6. Подтверждение только инициатором.
7. Повторная проверка прав и параметров.
8. Проверка срока действия запроса.
9. Выполнение операции.
10. Запись результата в журнал.

Подтверждения должны иметь срок действия 5 минут.

Повторное нажатие не должно приводить к повторному выполнению действия.

Истёкшие подтверждения должны автоматически становиться недействительными.

**Важно:** решение о безопасности операции принимает программная система, а не сама нейросеть. Нельзя доверять LLM проверку Discord-разрешений.

## 7. Контекст и память Mirei

Необходимо реализовать несколько видов памяти.

### Контекст диалога
Хранение последних сообщений для понимания текущего разговора.

### Контекст сервера
Информация о:
- Каналах.
- Категориях.
- Ролях.
- Настройках модулей.
- Правилах.
- Системах безопасности.

### Контекст пользователя
Информация, необходимая для персонализации общения и понимания предыдущих запросов.

Необходимо предусмотреть изоляцию данных разных Discord-серверов.

Mirei не должна переносить данные одного сервера в другой.

Также необходимо предусмотреть ограничения хранения, очистку устаревшей информации и возможность управления памятью.

## 8. Система инструментов AI Tools

Предлагается создать единый реестр инструментов.

Примеры:

- get_verification_stats
- get_trap_events
- get_member_roles
- get_server_stats
- create_private_channel
- get_audit_logs
- ban_member
- kick_member
- update_server_config
- get_module_status

Каждый инструмент должен иметь:
- Уникальное название.
- Описание назначения.
- Схему входных параметров.
- Проверку корректности параметров.
- Проверку разрешений.
- Уровень опасности.
- Обработку ошибок.
- Структурированный результат.

Нейросеть должна получать список доступных инструментов и выбирать подходящий.

Необходимо исключить прямое выполнение произвольного Python-кода, SQL-запросов и команд операционной системы по указанию модели.

## 9. Диагностика и самостоятельный контроль

Добавить возможность:

«Mirei, проверь состояние всех модулей».

Mirei должна проверять:
- Доступность модулей.
- Состояние подключений.
- Ошибки API.
- Доступность необходимых Discord-каналов.
- Наличие необходимых разрешений у бота.
- Работоспособность подключения к базе данных.

Результат должен содержать:
- Название модуля.
- Текущее состояние.
- Обнаруженные ошибки.
- Возможную причину.
- Рекомендацию по устранению.

Необходимо различать ситуацию, когда модуль действительно неисправен, и ситуацию, когда его состояние просто невозможно проверить.

## 10. Технические требования

В первую очередь необходимо изучить фактическую архитектуру проекта.

Предполагаемая технология:
- Python для Discord-бота.
- discord.py или disnake — в зависимости от фактического проекта.
- C# / ASP.NET Core .NET 8 для REST API, если backend уже существует или предусмотрен архитектурой.
- PostgreSQL для хранения данных.
- Существующие ИИ-провайдеры Mirei.

Не нужно создавать новые сервисы или переносить существующую бизнес-логику без необходимости.

Если модуль уже реализован в Python, можно подключить его через Python-адаптер.

Если функциональность уже доступна через REST API, использовать существующий API.

Необходимо соблюдать текущие соглашения об именовании, структуру базы данных и архитектуру проекта.

## 12. План реализации

Разработка должна выполняться поэтапно.

Этап 1. Анализ проекта.
- Изучить структуру файлов.
- Найти все существующие модули.
- Определить их функции и зависимости.
- Найти существующие API и модели.
- Проверить текущую реализацию Mirei.
- Подготовить карту интеграции.

Этап 2. Создание AI Tool Router.
- Реализовать реестр инструментов.
- Создать единый интерфейс вызова.
- Реализовать обработку результатов и ошибок.

Этап 3. Создание Security Layer.
- Реализовать проверку разрешений.
- Добавить классификацию опасных операций.
- Добавить подтверждения.
- Реализовать защиту от повторного выполнения.

Этап 4. Интеграция существующих модулей.
- Подключить верификацию.
- Подключить канал-ловушку.
- Подключить автоматические роли.
- Подключить статистику.
- Подключить приватные каналы.
- Подключить логи.

Этап 5. Интеграция с Mirei AI Core.
- Подключить выбор инструментов.
- Реализовать передачу контекста.
- Реализовать обработку результатов.
- Научить Mirei уточнять неоднозначные запросы.

Этап 6. Память и диагностика.
- Реализовать контекст сервера.
- Реализовать контекст пользователей.
- Добавить диагностику модулей.

Этап 7. Тестирование.
- Проверить корректность работы каждого инструмента.
- Проверить безопасность операций.
- Проверить подтверждения.
- Проверить обработку ошибок.
- Проверить работу при недоступности ИИ и API.
- Проверить изоляцию нескольких серверов.

## 13. Важные правила разработки

1. Не переписывать существующие модули без объективной необходимости.
2. Не удалять уже реализованные функции.
3. Не менять существующие команды и интерфейсы без необходимости.
4. Не создавать дубликаты уже существующих систем.
5. Не придумывать функции, которых нет в проекте.
6. Не считать интеграцию завершённой, пока она не проверена.
7. Не оставлять пустые обработчики и фиктивные реализации.
8. Не хранить токены и секреты непосредственно в исходном коде.
9. Не разрешать ИИ обходить проверки прав.
10. Сохранять совместимость с существующей архитектурой.

## 14. Что необходимо получить в результате

В результате должна получиться система, в которой Mirei:

- Понимает обычные запросы пользователей.
- Знает о существующих модулях сервера.
- Может получать данные из всех подключённых модулей.
- Может управлять их функциями.
- Проверяет права инициатора.
- Запрашивает подтверждение опасных действий.
- Ведёт журнал собственных операций.
- Умеет анализировать состояние сервера.
- Может сообщать об ошибках и проблемах.
- Использует память и контекст для более качественного общения.

**Итоговая цель: Mirei становится единым интеллектуальным центром управления Discord-сервером, а существующие модули остаются самостоятельными системами, которыми Mirei управляет через безопасный программный интерфейс.**
